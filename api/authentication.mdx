Every request you make to the PathPilot API must be authenticated with an API key. PathPilot uses Bearer token authentication — you include your API key in the `Authorization` header, and PathPilot validates it against your workspace before processing the request. There are no cookies, sessions, or OAuth flows required for server-to-server integrations.

## Creating an API Key

Generate a new API key directly from the PathPilot dashboard. You can create multiple keys — for example, one per integration or service — and revoke any key individually without affecting the others.

<Steps>
  <Step title="Navigate to API Keys settings">
    Sign in to your PathPilot workspace. Go to **Settings** in the left-hand navigation, then select **API Keys** from the settings menu.
  </Step>
  <Step title="Create a new key">
    Click **New Key** in the top-right corner of the API Keys page. A dialog will appear prompting you for key details.
  </Step>
  <Step title="Name your key and set an optional expiry">
    Enter a descriptive name for the key (for example, `ci-pipeline` or `slack-integration`). Optionally, set an expiration date. Keys without an expiry remain valid until you manually revoke them.
  </Step>
  <Step title="Copy your key">
    After clicking **Create**, PathPilot displays your new API key exactly once. Copy it immediately and store it securely — the full key value is never shown again after you close this dialog.
  </Step>
</Steps>

## Using the API Key

Pass your API key as a Bearer token in the `Authorization` header of every API request. The following example authenticates a request to list users in your workspace.

```bash
curl https://api.pathpilot.com/v1/users \
  -H "Authorization: Bearer pp_live_xxxxxxxxxxxx"
```

If your key is invalid, expired, or has been revoked, the API returns `401 Unauthorized` with an `invalid_api_key` error code. Check that you have copied the key correctly and that it has not been revoked in your dashboard.

## Key Format

PathPilot API keys are prefixed to make them easy to identify and to prevent accidental exposure in logs.

| Prefix      | Environment         | Use case                                      |
|-------------|---------------------|-----------------------------------------------|
| `pp_live_`  | Production          | Real workspace data; use in production systems |
| `pp_test_`  | Sandbox             | Safe for development and testing               |

Use `pp_test_` keys during development and in CI pipelines. Sandbox keys interact with an isolated copy of your workspace data and will not affect your live compliance records.

## Scopes

API keys are scoped to the workspace in which they are created. A key grants access to all resources within that workspace according to the permissions of the workspace role. Keys cannot be shared across workspaces.

For best security practices, create one key per integration rather than sharing a single key across multiple services. This makes it straightforward to revoke access for a specific integration without disrupting others.

## Rotating Keys

Rotate your API keys periodically or immediately after a suspected exposure. The safest rotation process avoids any downtime.

1. Create a new API key in **Settings → API Keys**.
2. Update your integration or secrets manager with the new key value.
3. Deploy the updated integration and verify it is functioning correctly.
4. Revoke the old API key from the dashboard.

## Revoking Keys

Revoke an API key at any time from **Settings → API Keys**. Locate the key by name, click **Revoke**, and confirm. Revocation takes effect immediately — all subsequent requests using that key will receive a `401 Unauthorized` response.

<Warning>
  PathPilot displays your API key **only once**, immediately after creation. Store it in a secrets manager (such as AWS Secrets Manager, HashiCorp Vault, or 1Password) before closing the creation dialog. If you lose a key, you must revoke it and generate a new one — there is no way to retrieve the original value.
</Warning>
