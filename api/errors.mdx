PathPilot uses conventional HTTP status codes to communicate the outcome of every API request. Codes in the `2xx` range indicate success. Codes in the `4xx` range indicate a problem with the request — usually a missing parameter, invalid credentials, or a permission issue that you can resolve. Codes in the `5xx` range indicate an unexpected problem on PathPilot's servers.

## Error Response Format

When a request fails, PathPilot returns a JSON body with an `error` object. The `code` field is a machine-readable string you can use for programmatic error handling. The `message` field is a human-readable description of what went wrong. Always include the `request_id` when contacting PathPilot support.

```json
{
  "error": {
    "code": "invalid_api_key",
    "message": "The API key provided is invalid or has been revoked.",
    "request_id": "req_abc123"
  }
}
```

## HTTP Status Codes

The following table lists every HTTP status code the PathPilot API returns and describes what each one means for your integration.

| Status Code                    | Meaning                                                                                  |
|-------------------------------|------------------------------------------------------------------------------------------|
| `200 OK`                      | The request succeeded. The response body contains the requested resource or result.      |
| `201 Created`                 | A new resource was successfully created. The response body contains the new resource.    |
| `204 No Content`              | The request succeeded but there is no response body (for example, after a `DELETE`).     |
| `400 Bad Request`             | The request was malformed or missing required parameters. Check the `error.message` field for details. |
| `401 Unauthorized`            | The API key is missing, invalid, or has been revoked. Verify your `Authorization` header. |
| `403 Forbidden`               | Your API key is valid, but it does not have permission to perform this action.           |
| `404 Not Found`               | The requested resource does not exist or has been deleted.                               |
| `409 Conflict`                | The request conflicts with the current state of the server, such as creating a duplicate resource. |
| `422 Unprocessable Entity`    | The request is syntactically valid but semantically incorrect — for example, an invalid date range or unsupported enum value. |
| `429 Too Many Requests`       | You have exceeded your plan's rate limit. Wait for the duration specified in the `Retry-After` header before retrying. |
| `500 Internal Server Error`   | An unexpected error occurred on PathPilot's servers. The issue is on our side — retry with exponential backoff. |

## Common Error Codes

PathPilot returns consistent machine-readable error codes across all endpoints. Use these codes to drive logic in your error-handling layer.

- **`invalid_api_key`** — The API key in the `Authorization` header is missing, malformed, or has been revoked. Generate a new key or check that you've copied the value correctly.
- **`insufficient_permissions`** — Your API key is valid, but the associated workspace role does not permit this action. Check the required permissions for the endpoint.
- **`resource_not_found`** — The resource identified by the ID in the request path does not exist in your workspace. Verify the ID and confirm the resource has not been deleted.
- **`validation_error`** — One or more request body parameters are invalid. The `error.message` field specifies which fields failed validation and why.
- **`rate_limit_exceeded`** — Your integration has sent too many requests within the current rate-limit window. Back off and retry after the `Retry-After` interval.
- **`workspace_suspended`** — Your PathPilot workspace has been suspended, typically due to a billing issue. Log in to the dashboard to resolve the suspension before retrying API requests.

## Retrying Requests

Not all errors are worth retrying. Use the following strategy to build a resilient integration.

**Retry** on `429 Too Many Requests` and `5xx` server errors. For `429`, respect the `Retry-After` response header. For `5xx` errors, use exponential backoff with jitter — for example, wait 1 second before the first retry, 2 seconds before the second, 4 seconds before the third, and so on, up to a maximum interval you define.

**Do not retry** on `4xx` errors other than `429`. A `400`, `401`, `403`, `404`, `409`, or `422` response indicates a problem with the request itself that will not resolve by sending the same request again. Fix the underlying issue in your integration before retrying.

```python
import time
import random
import requests

def request_with_backoff(url, headers, max_retries=5):
    for attempt in range(max_retries):
        response = requests.get(url, headers=headers)
        if response.status_code == 429:
            retry_after = int(response.headers.get("Retry-After", 2 ** attempt))
            time.sleep(retry_after)
        elif response.status_code >= 500:
            wait = (2 ** attempt) + random.uniform(0, 1)
            time.sleep(wait)
        else:
            return response
    raise Exception("Max retries exceeded")
```

<Tip>
  Log the `request_id` from every error response in your application logs. When you contact PathPilot support, sharing the `request_id` allows the support team to look up the exact request in our systems and diagnose the issue significantly faster.
</Tip>
